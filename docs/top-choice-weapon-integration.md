# Top-Choice weapon integration — INT-1 record (2026-11-11)

Owner adoption (2026-11-11): all rendered Top-Choice families are adopted
at their shipping shapes and the implementation hold is lifted. INT-1 is
the weapons slice (26 legendary paintings, Wave 1 + Wave 1.5; 36 weapon
base paintings, Wave 2). This document records the slice's premise check,
what INT-1 ships, and what remains for the follow-on renderer step. It is
the decision-capture home for the slice; the PR body carries the same
record.

## 1. Premise check — no sprites to swap; a production layer to build

The slice was briefed as a sprite swap. Against the code, that premise
was false in its specifics, and the slice was rebuilt around what the
repo actually holds:

- At base master `8f8a332b` the sprite manifest (307 entries,
  6,721,903 B) contained zero weapon entries (kinds: prop 184,
  background 45, enemy 39, character 39). Weapons are painted at runtime
  by two texel compositors (`weaponCompositor.ts` 120x44,
  `weaponCardCompositor.ts` 240x88 card + held) from authored data;
  `PixelWeapon.tsx` is canvas-only. Full Visual Program V4 (2026-11-08)
  removed the last bespoke legendary PNGs deliberately, and
  `src/test/pixelManifest.test.ts` pins the outcome: "the 26 legendary
  ids are NOT baked sprites anymore (V4: authored data)".
- The program books define the paintings' shipping class (palette-256
  at 1440 px card width) but defer per-surface integration: "final
  per-surface sizing is the step-3 pass" (Wave 1 book); "final shipped
  dimensions per surface (card, inspect, in-hand, wiki) are decided in
  the sizing pass that follows the owner's approval" (Wave 2 book).
  Wave 15 specifies integration mechanics for the wiki plates only.
- What the repo DOES have is a standing production pattern for exactly
  this shape of asset, set by the vistas slice (`src/lib/pixel/
  production.ts`): real content is registered in the sprite manifest
  *behind* its trim — a trimmed production sprite plus a measured trim
  record in a pure, Node-loadable module — never a loose file swap.
  INT-1 follows that pattern for weapons.

Replacing the compositors' output with the paintings inside
`PixelWeapon` / the stages is a further step, not this slice: it changes
the source of truth for weapon appearance (AGENTS.md routes that
through `docs/ARCHITECTURE.md` first), rewrites DESIGN.md section 8's
weapon law (this slice was briefed for no law change), and must answer
questions no program document rules on — per-item variety (seeded part
variants, affix decals, roll condition are stamped into today's
renders; one painting per type x manufacturer carries none of them) and
element rendering (in-game element reads exist only as compositor
effects; Wave 2 produced a palette-swap zone map for exactly one base,
beam-helixworks — the other 35 have glow-zone notes, not zone data).
Section 4 lists what that step needs. INT-1 builds everything it
consumes.

## 2. What INT-1 ships

### 2a. The production sprite layer (game side)

- **62 production sprites** in `src/assets/pixel/sprites/`, registered
  in the manifest by `scripts/sync-weapon-paintings.py`:
  - 26 legendaries — ids `legendary-painting-<slug>`, kind
    `weapon-legendary` (the union member that already existed for this
    family). The bespoke `legendary-<slug>` ids are NOT reused: they
    are the V4 authored-data identities, and the manifest test pins
    them as non-sprites.
  - 36 bases — ids `weapon-base-<type>-<maker>`, kind `weapon-base`
    (one literal added to `PixelSpriteKind`).
  - Sprite files are the palette-256, true-alpha, content-trimmed
    derivations at the books' 1440 px card-width class — the same
    files as the wiki sources (2b), byte-identical except where the
    sync content-cropped a soft edge (51 of 62 sprites cropped;
    -26,610 B across the slice).
  - Anchors are measured from each sprite's alpha mask by
    `scripts/pixel-key.py`'s own `compute_anchors` — the manifest's
    canonical anchor method, not hand-tuned values.
- **Trim records**: `src/lib/pixel/weaponPaintingData.ts` (generated by
  the sync; do not hand-edit) — per sprite, where its content sits on
  the adopted master's full canvas, in sprite pixels.
  `src/lib/pixel/spriteProduction.ts` owns the pure operations
  (trim / untrim / retrim; content = alpha > 8, the derivation
  recipe's threshold) and the id space. It loads in Node exactly like
  `legendaryArt.ts`, so the wiki generator and tests share it.
- **Kind + round-trip test**: `src/test/weaponKinds.test.ts` asserts
  all 62 registrations and kinds, and the full round-trip per sprite
  (untrim onto the master canvas, re-measure the identical record,
  trim back out pixel-identical), modeled on production.ts's cited
  test pattern.
- **Palette codec**: `src/lib/pixel/pngCodec.ts` gains
  `encodePalettePng` (color type 3 + tRNS, per-row filter selection) —
  a pure addition; the existing RGBA codec is untouched.

### 2b. The wiki re-point (Wave 15 A1/A2)

- **Painted sources**: `scripts/wiki-gen/assets/weapons/` — the same
  62 derivations, produced by `scripts/wiki-gen/derive-weapon-
  paintings.py` from the adopted masters (key_white keying, content
  crop, 1440 px class, palette-256 FASTOCTREE; per-file provenance in
  `assets/weapons/sources.json`, folder README beside them).
- **Generator**: `scripts/wiki-gen/images.ts` (`legendaryPlates`) and
  `images-w5.ts` (`weaponFramePlates`) fit the paintings into the
  480x176 plate boxes by Wave 15's recipe (bare object on transparency,
  box minus 28 px, centered; premultiplied-alpha area-average fit;
  fitted pixels snapped to the master's own palette and published as
  palette-256 PNGs — the form Wave 15 priced for these classes).
  Three sets must agree 1:1 or the build fails: the enumeration
  (legendary parity fixture / type x manufacturer table), the
  production data (`weaponPaintingData.ts`), and the source files.
- **Element reads (A3) are unchanged, deliberately.** Wave 15: the
  reads re-derive "from the new bases" through the compositor, and
  tinting a master to fake one "was considered and rejected: it would
  misstate the art (the reads' lighting is geometry-aware compositor
  work) and break the one-render signature." The new bases now exist
  as production sprites (2a); the reads' in-game lighting still has no
  painterly source, so the generator's compositor derivation remains
  the honest source and the 36 element plates are byte-identical.

- Entries: 307 → **369**. Payload: 6,721,903 B → **12,048,353 B**.
- Per-family: legendary paintings **+2,903,472 B** (26 sprites);
  weapon base paintings **+2,422,978 B** (36 sprites). Slice delta

- Ceiling pin (`src/test/overhaulVisuals.test.ts`): **11,620,000 →
  12,066,000**, with the accounting in the test's comment history in
  the established pattern (~17 KB headroom, the M4 discipline). The
  consolidated ledger's program-level figure (~81M across all adopted
  families) lands family by family as each slice registers its
  sprites with its own accounting — this slice is the first.
- Wiki payload (web, not app): the 62 re-pointed plates grow from
  130,429 B (62,358 legendary + 68,071 frames) to **892,818 B

  403,097 B + 403,982 B; INT-1's plates run ~11% over that estimate
  because they are fitted from the card-width masters rather than
  the native masters and carry the silhouette-pass masters for the
  15 re-done legendaries (see 5).

## 4. What the renderer step still needs (not INT-1)

1. An ARCHITECTURE.md source-of-truth update + DESIGN.md section 8
   amendment for painted weapon rendering (owner sign-off).
2. A ruling on per-item variety under paintings: variety dies, or the
   paintings become a base layer under re-implemented dynamic systems
   (decals / condition / element as raster overlays).
3. Element zone data for the 35 bases without zone maps (Wave 2's
   zone-proof method, per base), if element reads are to light the
   paintings in game or in the wiki.
4. Golden baseline re-strike (Wave 15 C1) in that slice, and in-game
   captures at phone width on both renderers per the program BRIEF's
   acceptance checks.

## 5. Findings recorded, not smoothed over

- **Wave 15's legendary proof plates used superseded art for 15
  slugs.** Its `derive.py` mapped every legendary plate to
  `wave1-legendaries/renders/`, but the adopted set (consolidated
  ledger D-3, verified arithmetically from disk: 7,130,362 -
  4,127,981 + 5,081,893 = 8,084,274 B) replaces 15 of the 26 with the
  Wave 1.5 silhouette-pass masters. INT-1 derives from the adopted
  masters throughout; its plates and sprites for those 15 differ
  from Wave 15's proof plates, correctly.
- **The "bench-basic" fix item is unresolvable as specified.** The
  consolidated ledger names "the bench-basic base's doubled amber
  panel" as an integration fix, "recorded in the wave book". No base
  by that name, and no such direction, exists in the Wave 2 NOTES,
  the Wave 2 book's full text (including its six owner calls), the
  Wave 1 book, or the ledger beyond that one line; the 36 bases are
  fully enumerated in Wave 2's per-base table and none matches the
  description. No painting was edited. The item needs the parent to
  identify the base and panel before it can be actioned.
